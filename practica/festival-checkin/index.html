Lee las filas antes de abrir el JSON

En Events, una fila es un evento. En Registrations, una fila es la inscripción de una persona a un evento. Estas filas son ejemplos para entender el modelo.

Cargando el ejemplo…

Fíjate en evt-001. En Events identifica «Festival de otoño». En Registrations agrupa a las dos personas inscritas. La pareja evt-001 + equipo-02 identifica una sola inscripción. Esa fila tiene checkedInAt, así que esa persona ya ha entrado. En la otra fila, el guion indica que aún no hay hora de entrada.

Compruébalo · ¿qué pasa si equipo-01 se apunta a otro evento?

La nueva inscripción tendría eventId = evt-002 y userId = equipo-01. Es una pareja de claves distinta. Si buscas por evt-001, siguen saliendo solo las dos filas del primer evento.

Ver cómo se escribe el modelo en JSON

Buscad DataModel. Ahí hay una definición por tabla. Dentro de cada una, buscad estas tres partes.

TableName
El nombre que veis encima de cada tabla.
KeyAttributes
Las claves que el visor marca como PK y SK. AttributeName es el nombre del campo y S significa texto. En Events, el nombre de SortKey está vacío porque esa tabla solo tiene PK.
TableData
Las filas ficticias. { "S": "evt-001" } guarda el texto evt-001. La vista de tabla muestra directamente ese valor.

NonKeyAttributes enumera campos como title y registeredAt. Para esta primera lectura podéis pasar por alto los metadatos, DataAccess y la lista vacía de índices.

Crear y comprobar desde la terminal

Cambiad equipo-01 por vuestro prefijo. Anotad los nombres que resulten para la pestaña Lectura.

equipo=equipo-01
tabla_eventos="$equipo-events"
tabla_inscripciones="$equipo-registrations"
1 · Crear Events con eventId como PK 
aws dynamodb create-table \
  --profile "$perfil" --region "$region" \
  --table-name "$tabla_eventos" \
  --attribute-definitions AttributeName=eventId,AttributeType=S \
  --key-schema AttributeName=eventId,KeyType=HASH \
  --billing-mode PAY_PER_REQUEST \
  --query 'TableDescription.TableStatus' --output text

La salida inicial suele ser CREATING. S significa texto. HASH indica la clave de partición.

2 · Crear Registrations con eventId como PK y userId como SK 
aws dynamodb create-table \
  --profile "$perfil" --region "$region" \
  --table-name "$tabla_inscripciones" \
  --attribute-definitions AttributeName=eventId,AttributeType=S AttributeName=userId,AttributeType=S \
  --key-schema AttributeName=eventId,KeyType=HASH AttributeName=userId,KeyType=RANGE \
  --billing-mode PAY_PER_REQUEST \
  --query 'TableDescription.TableStatus' --output text

RANGE indica la clave de ordenación. Dos personas inscritas en el mismo evento comparten eventId y se distinguen por userId.

3 · Esperar y revisar las claves 
for tabla in "$tabla_eventos" "$tabla_inscripciones"; do
  aws dynamodb wait table-exists \
    --profile "$perfil" --region "$region" --table-name "$tabla" || break
  aws dynamodb describe-table \
    --profile "$perfil" --region "$region" --table-name "$tabla" \
    --query 'Table.{Nombre:TableName,Estado:TableStatus,Claves:KeySchema}' || break
done

Esperad ACTIVE en ambas. Events tiene solo eventId como HASH. Registrations tiene además userId como RANGE. Si una tabla ya existía, comprobad sus claves en este paso antes de continuar.

4 · Cargar y consultar con PartiQL 
aws dynamodb execute-statement \
  --profile "$perfil" --region "$region" \
  --statement "INSERT INTO \"$tabla_eventos\" VALUE {'eventId': 'evt-001', 'title': 'Festival de otoño'}"

aws dynamodb execute-statement \
  --profile "$perfil" --region "$region" --consistent-read \
  --statement "SELECT eventId, title FROM \"$tabla_eventos\" WHERE eventId = 'evt-001'"

aws dynamodb execute-statement \
  --profile "$perfil" --region "$region" --consistent-read \
  --statement "SELECT * FROM \"$tabla_inscripciones\" WHERE eventId = 'evt-001'"

Si el INSERT indica que el evento ya existe, comprobadlo con el SELECT. El primer SELECT devuelve evt-001 y Festival de otoño. El segundo devuelve Items: [] antes de registrar inscripciones.

async function checkIn(key) {

export async function handler(event) {
  const { eventId, userId } = event.pathParameters ?? {};
  const method = event.requestContext?.http?.method;
  if (eventId !== 'evt-001' || !/^equipo-\d{2}$/.test(userId ?? '')) {
    return json(400, { message: 'Usa evt-001 y un código equipo-00 a equipo-99' });
  }

  const key = { eventId, userId };
  try {
    if (method === 'GET') return await getPass(key);
    if (method === 'POST') return await register(key);
    if (method === 'PATCH') return await checkIn(key);
    return json(405, { message: 'Método no permitido' });
  } catch (error) {
    if (error.name === 'ConditionalCheckFailedException') {
      return json(409, { message: 'La operación no se puede aplicar a este estado' });
    }
    console.error(error.name, error.message);
    return json(500, { message: 'Revisa los logs de la función' });
  }
}

Contrato GET 200: { "eventId": "evt-001", "title": "Festival de otoño", "registration": null }. Si hay inscripción, sustituye null por un objeto con userId, registeredAt y, si existe, checkedInAt.

Antes de avanzar: la pantalla muestra el título real y «Sin inscripción».

Una inscripción por pareja de claves

  1. Completad register. Comprobad que existe el evento y guardad un ítem con ambas claves y registeredAt en UTC, asignado en Lambda.
  2. Condicionad el PutCommand a que no exista el ítem. Devolved 201 con un JSON de confirmación. La condición fallida se transforma en 409 en el esqueleto.
  3. Añadid POST /events/{eventId}/registrations/{userId} a la misma integración.

Antes de avanzar: pulsad Inscribirse dos veces. La primera devuelve 201 y la segunda 409. En DynamoDB hay un solo ítem para el equipo y la hora original se conserva.

Registrar la entrada

  1. Completad checkIn con UpdateCommand. Añadid checkedInAt en UTC. La condición exige una inscripción existente y que todavía no tenga checkedInAt.
  2. Devolved 200 con un JSON de confirmación. Añadid PATCH /events/{eventId}/registrations/{userId} a la API.
  3. Probad con un código nuevo y después con el código que sí se inscribió.

Antes de avanzar: un código nuevo recibe 409 y no crea un ítem. El inscrito recibe 200 y conserva ambas horas. Repetir la entrada devuelve 409.
