Un pase para el Festival de otoño

El usuario usuario-02 quiere asistir al Festival de otoño. En la puerta debemos saber si se inscribió y si ya entró. Construirás el pase y podrás demostrarlo desde la web, la API y DynamoDB.

Del caso de uso al diseño de datos

Dibuja las entidades y sus relaciones

Un usuario puede inscribirse en varios eventos y cada evento puede tener varios usuarios inscritos. Es una relación muchos a muchos. INSCRIPCION representa ese vínculo y guarda dos hechos propios: cuándo se inscribió el usuario y cuándo entró.

EVENTO

eventIdTítulo
10..N

INSCRIPCION

eventId + userIdFecha de inscripciónFecha de entrada, opcional
0..N1

USUARIO

userIdIdentificador del usuario
Prueba el modelo. El usuario usuario-02 puede tener una inscripción en evt-001 y otra en evt-002. La fecha de entrada de cada inscripción pertenece a su evento. Para probar la API del laboratorio usarás evt-001.

Antes de avanzar Escribe las dos parejas de identificadores. Comprueba que comparten userId y tienen distintos eventId.

De las preguntas a las claves de DynamoDB

Elige una pregunta. Fíjate en el dato que llega con la petición y en la clave que te permite localizar la respuesta.

Un evento

En EVENTO, eventId es la clave de partición (PK). Como cada evento tiene un identificador único, con evt-001 ya puedes recuperar su título.

EVENTO → PK evt-001 → Festival de otoño

Todas las inscripciones de un evento

En INSCRIPCION, la PK sigue siendo eventId. Una consulta por evt-001 recupera su grupo de inscripciones.

INSCRIPCION → PK evt-001 → usuario-01, usuario-02

Una inscripción concreta

Dentro del grupo, userId es la clave de ordenación (SK). La pareja completa identifica la inscripción. Su atributo checkedInAt indica si ya se registró la entrada.

INSCRIPCION → PK evt-001 + SK usuario-02 → una fila
Truco de diseño. Pregunta qué dato tienes al buscar. Si más adelante necesitas todos los eventos de un usuario y solo recibes userId, plantéate un índice con userId como clave de partición.

Antes de avanzar Abre las dos preguntas sobre inscripciones. En ambas tienes evt-001. La búsqueda de un pase añade usuario-02.

Convierte el modelo en dos tablas y pruébalo

Convención de Base de Datos. Escribe los nombres de tabla en singular y mayúsculas. Separa las palabras con barra baja, como en LINEA_PEDIDO. En esta práctica, EVENTO e INSCRIPCION llevan además el sufijo de tu equipo en AWS.

Evento → EVENTO. Guarda eventId y title. Inscripción → INSCRIPCION. Guarda la pareja de identificadores, registeredAt y, al entrar, checkedInAt.

En este caso, USUARIO es una entidad del diagrama. El pase recibe su userId y INSCRIPCION guarda esa referencia. Si el festival necesita guardar perfiles, podrá añadir una tabla USUARIO. En un modelo relacional, la clave foránea de la inscripción referencia al evento y la base de datos puede exigir que exista. Aquí eventId forma parte de la clave de DynamoDB y POST comprueba en la API que el evento existe antes de inscribir al usuario.

EVENTO
eventId · PK
1 ─── 0..N
INSCRIPCION
eventId · PK
userId · SK

La web del festival puede enviar peticiones a la API.

Cómo se comunica la web con API Gateway

httpApi:
Abre la configuración de la API HTTP de API Gateway, el servicio que recibe las peticiones de la web.
payload: '2.0'
Indica el formato que API Gateway usa para entregar la petición a Lambda. El código lee el método en event.requestContext.http.method. Las comillas hacen que YAML lea 2.0 como texto.

Agrupa las reglas que consulta el navegador cuando la web y la API están en orígenes distintos.

Lista los orígenes web permitidos. El guion introduce https://albertohdezakkari.github.io como elemento de la lista.

Lista las cabeceras admitidas desde el navegador. Content-Type indica el tipo de contenido enviado.

Lista los métodos que puede usar la web: GET para consultar el pase, POST para inscribirse y PATCH para registrar la entrada. Cada guion añade un método.

Cómo se crea EVENTO

resources: → Resources:
El primer bloque pertenece a Serverless Framework. Dentro, Resources, con mayúscula, lista los recursos que crea CloudFormation.
EventsTable:
Identificador lógico que elegimos para la tabla de eventos. Es el mismo que aparece en Ref: EventsTable.
Type: AWS::DynamoDB::Table
Indica a CloudFormation qué tipo de recurso debe crear: una tabla DynamoDB.
Properties:
Agrupa los ajustes de esa tabla.
TableName:
Fija el nombre real en AWS. Con TABLE_SUFFIX=01 se crea EVENTO_01.
BillingMode: PAY_PER_REQUEST
Selecciona el modo bajo demanda. Las lecturas y escrituras se cobran según el uso.
AttributeDefinitions:
Lista los atributos que forman las claves y su tipo. AttributeName: eventId da el nombre del atributo y AttributeType: S lo declara de tipo texto.
KeySchema:
Lista qué papel cumple cada atributo en la clave. AttributeName repite el nombre del atributo y KeyType: HASH lo declara clave de partición. En esta tabla, eventId basta para localizar evt-001.

¿Qué valor necesitas para buscar el evento Festival de otoño en EventsTable?

Puedes localizar la inscripción de un usuario dentro de un evento.

Por qué INSCRIPCION necesita dos valores

RegistrationsTable:
Identificador lógico de la tabla de inscripciones. Type, Properties y BillingMode tienen la misma función que en EventsTable.
AttributeDefinitions:
Contiene dos elementos: eventId y userId. El campo AttributeType: S indica que ambos valores son texto.
TableName:
Con TABLE_SUFFIX=01 se crea INSCRIPCION_01.
KeySchema:
Define la clave compuesta de la tabla. eventId agrupa las inscripciones y userId distingue a cada usuario dentro del grupo.
KeyType: HASH
eventId es la clave de partición y permite agrupar las inscripciones por evento.
KeyType: RANGE
userId es la clave de ordenación y distingue a cada usuario dentro del evento. (evt-001, usuario-01) y (evt-001, usuario-02) son dos claves completas distintas.

API Gateway llama a handler(event)

event.pathParameters contiene los dos valores de la ruta. Aquí llegan eventId = evt-001 y userId = usuario-02. Si el formato es incorrecto, la función responde 400.

El método HTTP indica qué acción hacer

GET → getPass consulta el pase, POST → register inscribe y PATCH → checkIn registra la entrada. Las tres funciones reciben la misma pareja { eventId, userId }.

Del YAML a process.env

  1. Declaras la referenciaprovider.environmentEn serverless.yml, EVENTS_TABLE apunta a Ref: EventsTable.
  2. CloudFormation resuelve el nombreEVENTS_TABLE=EVENTO_01El despliegue configura esta variable en Lambda con el nombre de la tabla del equipo 01.
  3. Lambda lee el valorprocess.env.EVENTS_TABLEEn index.mjs, eventsTable recibe EVENTO_01. El mismo recorrido da INSCRIPCION_01 a registrationsTable.

export async function handler(event) {
  const { eventId, userId } = event.pathParameters ?? {};
  const method = event.requestContext?.http?.method;
  if (eventId !== 'evt-001' || !/^(?:usuario|equipo)-\d{2}$/.test(userId ?? '')) {
    return json(400, { message: 'Usa evt-001 y un código usuario-00 a usuario-99' });
  }

  const key = { eventId, userId };
  try {
    if (method === 'GET') return await getPass(key);
    if (method === 'POST') return await register(key);
    if (method === 'PATCH') return await checkIn(key);
    return json(405, { message: 'Método no permitido' });
  } catch (error) {
    if (error.name === 'ConditionalCheckFailedException') {
      return json(409, { message: 'La operación no se puede aplicar a este estado' });
    }
    console.error(error.name, error.message);
    return json(500, { message: 'Revisa los logs de la función' });
  }
}

async function register(key) {
  const { Item: event } = await db.send(new GetCommand({
    TableName: eventsTable,
    Key: { eventId: key.eventId },
    ConsistentRead: true
  }));
  if (!event) return json(404, { message: 'Evento no encontrado' });

  await db.send(new PutCommand({
    TableName: registrationsTable,
    Item: { ...key, registeredAt: new Date().toISOString() },
    ConditionExpression: 'attribute_not_exists(eventId)'
  }));
  return json(201, { message: 'Inscripción creada' });
}

async function checkIn(key) {
  await db.send(new UpdateCommand({
    TableName: registrationsTable,
    Key: key,
    UpdateExpression: 'SET checkedInAt = :hora',
    ConditionExpression: 'attribute_exists(eventId) AND attribute_not_exists(checkedInAt)',
    ExpressionAttributeValues: { ':hora': new Date().toISOString() }
  }));
  return json(200, { message: 'Entrada registrada' });
}
