El usuario usuario-02 quiere asistir al Festival de otoño. En la puerta debemos saber si se inscribió y si ya entró. Construirás el pase y podrás demostrarlo desde la web, la API y DynamoDB.

Del caso de uso al diseño de datos

Del diagrama entidad–relación a DynamoDB

Un usuario puede inscribirse en varios eventos y cada evento puede tener varios usuarios inscritos. INSCRIPCION representa ese vínculo muchos a muchos y guarda cuándo se inscribió el usuario y cuándo entró.

Dos consultas sobre las mismas inscripciones

  • Tabla FCI_INSCRIPCIONES · Query Usuarios de un evento

    Busca por EVENT_ID, la clave de partición. En este ejemplo, 1 devuelve usuario-01 y usuario-02.

  • Índice PorUsuario · Query Eventos de un usuario

    Busca por USER_ID, la clave de partición del índice. En este ejemplo, usuario-02 devuelve 1 y 2.

Antes de avanzar Comprueba en cuál de las dos consultas empiezas por 1 y en cuál por usuario-02. Después prueba el pase en el móvil. Puedes ejecutar ambas consultas en Validar → Consultar índice.

De las preguntas a las claves de DynamoDB

Elige una pregunta. Fíjate en el dato que llega con la petición y en la clave que te permite localizar la respuesta.

Un evento

En EVENTOS, EVENT_ID es la clave de partición (PK). Como cada evento tiene un identificador único, con 1 ya puedes recuperar su título.

EVENTOS → PK 1 → Festival de otoño

Todas las inscripciones de un evento

En INSCRIPCIONES, la PK sigue siendo EVENT_ID. Una consulta por 1 recupera su grupo de inscripciones.

INSCRIPCIONES → PK 1 → usuario-01, usuario-02

Una inscripción concreta

Dentro del grupo, USER_ID es la clave de ordenación (SK). La pareja EVENT_ID + USER_ID es la clave primaria compuesta. Su atributo CHECKED_IN_AT indica si ya se registró la entrada.

INSCRIPCIONES → PK 1 + SK usuario-02 → una fila

Los eventos de un usuario

Guardas cada inscripción una vez. DynamoDB mantiene el índice PorUsuario, que agrupa esas inscripciones por USER_ID (PK) y las ordena por EVENT_ID (SK).

PorUsuario → PK usuario-02 → 1, 2

Antes de avanzar Compara «¿Quién se ha inscrito al evento?» con «¿En qué eventos está inscrito usuario-02?». En la primera, entra por EVENT_ID en la tabla. En la segunda, entra por USER_ID en el índice. Probarás ambas búsquedas en Validar → Consultar índice.

Convierte el modelo en dos tablas y pruébalo

Escribe los atributos de DynamoDB en mayúsculas con guion bajo, como EVENT_ID. Cuando la API recibe o devuelve JSON, usa nombres como eventId. Verás cómo traducirlos en Lectura.

Convención de Base de Datos. Llama a las entidades Evento e Inscripción. Usa la abreviatura del proyecto, un guion bajo y el nombre de la tabla en plural. En Festival Check-in obtienes FCI_EVENTOS y FCI_INSCRIPCIONES. «San Valentín» sería el título de un evento guardado en FCI_EVENTOS.

Evento → EVENTOS. Guarda EVENT_ID y TITLE. Inscripción → INSCRIPCIONES. Guarda la pareja de identificadores, el número automático REGISTRATION_ID, REGISTERED_AT y, al entrar, CHECKED_IN_AT.

EVENT_ID y USER_ID son referencias al evento y a la persona, como dos claves foráneas en un modelo relacional. REGISTRATION_ID identifica la inscripción y se guarda como un atributo del ítem. La clave de DynamoDB sigue siendo la pareja EVENT_ID + USER_ID, que garantiza una inscripción por persona y evento.

En este caso, USUARIO es una entidad del diagrama. El pase recibe su USER_ID y INSCRIPCIONES guarda esa referencia. Si el festival necesita guardar perfiles, podrá añadir una tabla USUARIOS. En un modelo relacional, la clave foránea de la inscripción referencia al evento y la base de datos puede exigir que exista. Aquí EVENT_ID forma parte de la clave de DynamoDB y POST comprueba en la API que el evento existe antes de inscribir al usuario.

EVENTOS
EVENT_ID · PK
1 ─── 0..N
INSCRIPCIONES
EVENT_ID · PK
USER_ID · SK

Selecciona el equipo y el rol de Lambda

Quién actúa en cada momento. Tu perfil ejecuta el despliegue. El rol LabRole da permisos a Lambda cuando atiende una petición y necesita acceder a DynamoDB.

En Conectar → Comprobación verificaste tu perfil y tu región. El bloque de abajo vuelve a asignarlos para que puedas ejecutarlo también desde una terminal nueva. Cambia default por academy si guardaste las credenciales bajo [academy]. Si tu laboratorio usa otra región, sustituye us-east-1 por la que comprobaste.

AWS_PROFILE
Copia el nombre del perfil de $perfil. Las credenciales temporales están en el perfil que guardaste en ~/.aws/credentials.
AWS_REGION
Copia $region. Serverless usa ese valor en provider.region.
LAMBDA_ROLE_ARN
El comando aws iam get-role consulta el identificador del rol existente LabRole y lo guarda en esta variable.

Ejecuta el bloque desde la carpeta festival-checkin.

perfil=default
region=us-east-1
export AWS_PROFILE="$perfil"
export AWS_REGION="$region"
LAMBDA_ROLE_ARN=$(aws iam get-role --role-name LabRole --profile "$perfil" --region "$region" --query 'Role.Arn' --output text) &&
  export LAMBDA_ROLE_ARN &&
  printf 'AWS_PROFILE=%s\nAWS_REGION=%s\nLAMBDA_ROLE_ARN=%s\n' \
    "$AWS_PROFILE" "$AWS_REGION" "$LAMBDA_ROLE_ARN"

Si el laboratorio deniega iam:GetRole, consulta las instrucciones del laboratorio o solicita el ARN autorizado para tu cuenta. Escríbelo con export LAMBDA_ROLE_ARN="ARN_DEL_LAB", sustituyendo el valor entre comillas.

Antes de avanzar Comprueba que la salida muestra tu perfil, tu región y el ARN de LabRole.

La web del festival puede enviar peticiones a la API.

Cómo se comunica la web con API Gateway

httpApi:
Abre la configuración de la API HTTP de API Gateway, el servicio que recibe las peticiones de la web.
payload: '2.0'
Indica el formato que API Gateway usa para entregar la petición a Lambda. El código lee el método en event.requestContext.http.method. Las comillas hacen que YAML lea 2.0 como texto.
cors:
Agrupa las reglas que consulta el navegador cuando la web y la API están en orígenes distintos.
allowedOrigins:
Lista los orígenes web permitidos. El guion introduce https://albertohdezakkari.github.io como elemento de la lista.
allowedHeaders:
Lista las cabeceras admitidas desde el navegador. Content-Type indica el tipo de contenido enviado.
allowedMethods:
Lista los métodos que puede usar la web: GET para consultar el pase, POST para inscribirse y PATCH para registrar la entrada. Cada guion añade un método.

Busca el guion delante de PATCH. Marca un elemento de la lista allowedMethods.

Cada operación tiene su propia Lambda. API Gateway la elige por el método HTTP y la ruta.

Cómo una ruta llega a su archivo

build:
Abre los ajustes de preparación del código para el despliegue.
esbuild: false
false es un valor booleano. Aquí desactiva la herramienta integrada esbuild porque desplegamos los módulos JavaScript de src/.
functions:
Agrupa las funciones Lambda del servicio.
consultarPase:
Lambda que consulta el pase cuando API Gateway recibe GET en la ruta del pase.
handler: src/pases/consultar.handler
src/pases/consultar identifica el archivo consultar.mjs. Lambda ejecuta su función exportada handler.
inscribirUsuario:
Lambda que crea la inscripción cuando API Gateway recibe POST en la ruta del pase.
handler: src/pases/inscribir.handler
src/pases/inscribir identifica el archivo inscribir.mjs. Lambda ejecuta su función exportada handler.
crearEvento:
Lambda que invocas desde la terminal para asignar un ID y guardar un evento. name fija el nombre usado por AWS CLI.
registrarEntrada:
Lambda que registra la entrada cuando API Gateway recibe PATCH en la ruta del pase.
handler: src/pases/entrada.handler
src/pases/entrada identifica el archivo entrada.mjs. Lambda ejecuta su función exportada handler.

Lista lo que puede activar esa Lambda. Cada - httpApi: añade una ruta HTTP.

Selecciona el método HTTP de la ruta. Junto con path, identifica la ruta que activa el handler de ese bloque.

Define la dirección que se compara con la petición. En /events/1/registrations/usuario-02, las llaves de la plantilla marcan los huecos: {eventId} recibe 1 y {userId} recibe usuario-02.

Cómo se crea EVENTOS

resources: → Resources:
El primer bloque pertenece a Serverless Framework. Dentro, Resources, con mayúscula, lista los recursos que crea CloudFormation.
FestivalCheckInEventos:
Identificador lógico que indica el proyecto y qué guarda la tabla. Usa este nombre exacto en Ref: FestivalCheckInEventos.
Type: AWS::DynamoDB::Table
Indica a CloudFormation qué tipo de recurso debe crear: una tabla DynamoDB.
Properties:
Agrupa los ajustes de esa tabla.
TableName:
Fija el nombre real en AWS, FCI_EVENTOS.
BillingMode: PAY_PER_REQUEST
Selecciona el modo bajo demanda. Las lecturas y escrituras se cobran según el uso.
AttributeDefinitions:
Lista los atributos que forman las claves y su tipo. AttributeName: EVENT_ID da el nombre del atributo y AttributeType: N lo declara de tipo numérico.
KeySchema:
Lista qué papel cumple cada atributo en la clave. AttributeName repite el nombre del atributo y KeyType: HASH lo declara clave de partición. En esta tabla, EVENT_ID basta para localizar 1.

¿Qué valor necesitas para buscar el evento Festival de otoño en FestivalCheckInEventos?

Puedes localizar la inscripción de un usuario dentro de un evento.

Por qué INSCRIPCIONES necesita dos valores

FestivalCheckInInscripciones:
Identificador lógico de las inscripciones de Festival Check-in. Usa Ref: FestivalCheckInInscripciones cuando necesites su nombre físico.
AttributeDefinitions:
Contiene dos elementos: EVENT_ID y USER_ID. EVENT_ID es numérico (N) y USER_ID es texto (S).
TableName:
Fija el nombre real en AWS, FCI_INSCRIPCIONES.
KeySchema:
Define la clave compuesta de la tabla. EVENT_ID agrupa las inscripciones y USER_ID distingue a cada usuario dentro del grupo.
KeyType: HASH
EVENT_ID es la clave de partición y permite agrupar las inscripciones por evento.
KeyType: RANGE
USER_ID es la clave de ordenación y distingue a cada usuario dentro del evento. (1, usuario-01) y (1, usuario-02) son dos claves completas distintas.

Si ya existe (1, usuario-01), ¿puedes guardar (1, usuario-02) como otra fila?

Puedes encontrar los eventos de un usuario con solo su código.

Cómo se crea el índice PorUsuario

GlobalSecondaryIndexes:
Declara los índices de FestivalCheckInInscripciones. Este índice añade otra forma de buscar las inscripciones de esa tabla.
IndexName:
Identifica el índice. Usa PorUsuario al hacer la consulta.
KeySchema:
Define las claves del índice. Usa el número EVENT_ID y el texto USER_ID ya declarados en AttributeDefinitions.
KeyType: HASH
USER_ID es la clave de partición del índice. Con usuario-02 localizas su grupo de inscripciones.
KeyType: RANGE
EVENT_ID es la clave de ordenación del índice. Ordena los eventos dentro de cada usuario.
ProjectionType: KEYS_ONLY
El índice guarda USER_ID y EVENT_ID. El número REGISTRATION_ID se lee en la tabla de inscripciones con esa pareja.

  runtime: nodejs22.x

      Ref: FestivalCheckInInscripciones
  httpApi:
    payload: '2.0'
    cors:
      allowedOrigins:
        - https://albertohdezakkari.github.io
      allowedHeaders:
        - Content-Type
      allowedMethods:
        - GET
        - POST
        - PATCH

  esbuild: false

          method: GET
          path: /events/{eventId}/registrations/{userId}
  inscribirUsuario:
    handler: src/pases/inscribir.handler
    events:
      - httpApi:
          method: POST
          path: /events/{eventId}/registrations/{userId}
  registrarEntrada:
    handler: src/pases/entrada.handler

          method: PATCH
          path: /events/{eventId}/registrations/{userId}

    FestivalCheckInEventos:

      Properties:
        TableName: FCI_EVENTOS
        BillingMode: PAY_PER_REQUEST

            AttributeType: N
        KeySchema:
          - AttributeName: EVENT_ID
            KeyType: HASH
    FestivalCheckInInscripciones:
      Type: AWS::DynamoDB::Table
      Properties:
        TableName: FCI_INSCRIPCIONES
        BillingMode: PAY_PER_REQUEST
        AttributeDefinitions:
          - AttributeName: EVENT_ID
            AttributeType: N
          - AttributeName: USER_ID
            AttributeType: S

            KeyType: HASH

import { DynamoDBClient } from '@aws-sdk/client-dynamodb';
import { DynamoDBDocumentClient, UpdateCommand } from '@aws-sdk/lib-dynamodb';

export const maxEventId = 9223372036854775807n;
export const db = DynamoDBDocumentClient.from(new DynamoDBClient({}));
export const tablaEventosFCI = process.env.FCI_TABLA_EVENTOS;
export const tablaInscripcionesFCI = process.env.FCI_TABLA_INSCRIPCIONES;

export async function nextId(counterName) {
  const { Attributes } = await db.send(new UpdateCommand({
    TableName: tablaEventosFCI,
    Key: { EVENT_ID: 0 },
    UpdateExpression: 'ADD #contador :uno',
    ConditionExpression: 'attribute_not_exists(#contador) OR #contador < :limite',
    ExpressionAttributeNames: { '#contador': counterName },
    ExpressionAttributeValues: { ':uno': 1, ':limite': maxEventId },
    ReturnValues: 'UPDATED_NEW'
  }));
  return Attributes[counterName];
}

Comparte el formato de respuesta y el tratamiento de errores de estas rutas. Si ya creaste el archivo con una versión anterior, sustituye la condición y el mensaje 400 por los de este ejemplo y actualiza json para serializar los identificadores grandes.

import { maxEventId } from '../datos/dynamo.mjs';

export function json(statusCode, body) {
  return {
    statusCode,
    headers: { 'content-type': 'application/json' },
    body: JSON.stringify(body, (_name, value) =>
      typeof value === 'bigint' ? value.toString() : value)
  };
}

export async function handleRequest(event, operation) {
  const { eventId: routeId, userId } = event.pathParameters ?? {};
  const eventId = /^[1-9]\d{0,18}$/.test(routeId ?? '') ? BigInt(routeId) : 0n;
  if (!eventId || eventId > maxEventId || !userId) {
    return json(400, { message: 'Indica un ID de evento entero positivo y un usuario' });
  }

  try {
    return await operation({ eventId, userId });
  } catch (error) {
    if (error.name === 'ConditionalCheckFailedException') {
      return json(409, { message: 'La operación no se puede aplicar a este estado' });
    }
    console.error(error.name, error.message);
    return json(500, { message: 'Revisa los logs de la función' });
  }
}

import { UpdateCommand } from '@aws-sdk/lib-dynamodb';
import { db, tablaInscripcionesFCI } from '../datos/dynamo.mjs';
import { handleRequest, json } from './peticion.mjs';

export function handler(event) {
  return handleRequest(event, checkIn);
}

async function checkIn(key) {
  await db.send(new UpdateCommand({
    TableName: tablaInscripcionesFCI,
    Key: { EVENT_ID: key.eventId, USER_ID: key.userId },
    UpdateExpression: 'SET CHECKED_IN_AT = :hora',
    ConditionExpression: 'attribute_exists(EVENT_ID) AND attribute_not_exists(CHECKED_IN_AT)',
    ExpressionAttributeValues: { ':hora': new Date().toISOString() }
  }));
  return json(200, { message: 'Entrada registrada' });
}

Del modelo al primer registro

Relaciona el JSON con las tablas

Buscad DataModel. Ahí hay una definición por tabla. Dentro de cada una, buscad estas tres partes.

TableName
El nombre que veis encima de cada tabla.
KeyAttributes
Las claves que el visor marca como PK y SK. AttributeName es el nombre del campo y S significa texto y N significa número. En EVENTOS, el nombre de SortKey está vacío porque esa tabla solo tiene PK.
TableData
Las filas ficticias. { "N": "1" } representa el número 1 en el formato de DynamoDB. La vista de tabla muestra directamente ese valor.

NonKeyAttributes enumera campos como TITLE y REGISTERED_AT. En GlobalSecondaryIndexes de INSCRIPCIONES puedes comparar las claves del índice PorUsuario con las de la tabla.
